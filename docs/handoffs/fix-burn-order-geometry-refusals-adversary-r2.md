## Three flagged items — judged

**(a) "An injected world time located beforehand by sweeping the clock against the same solver
and fixed in the test."** Acceptable. The solver is pure and its trigonometry is a pinned table,
so a fixed (body table, fleet state, world time) triple gives the same outcome on every run; the
constant in the test is an arrangement, not a sample. It is not vacuous: what the test asserts
is the handler's status and body at that instant, which is the requirement. Both outcomes
demonstrably exist (round-1 probe: 6,144 short and 35,328 solved of 41,472 at a ring-1
station; thousands of destination refusals at a ring-0 station). One thing would make it
robust, and is advice, not a finding: have each such test first assert, by a direct solver call
at the fixed instant, the sentinel it depends on, so a retune that moves the instant fails with
"arrangement no longer holds" and is not misread as a handler regression.

**(b) The two stop scenarios.** Probed at solver level for all seven star classes, with the
exact construction `Stop` uses (`pos + unit * 2 * MinArcLength`, `fleet/service.go:1343-1348`).
A fleet 1.0 outside the clearance heading straight at the star: the lead point is 3.0 inside
and `SolveBurn` returns `ErrEndpointInsideClearance` in 7 of 7. A fleet 1.0 inside: same
sentinel in 7 of 7, and under Decision 4 the origin pre-test catches it first. By reading, the
burn branch of `Stop` performs no write before the solve (`f.AttachedTo = ""` at `:1286` is in
memory only), so "stored attachment, motion state and fuel are unchanged" holds. The stationary
short-point arrangement returns `ErrArcTooShort` in 7 of 7, a point exactly on the clearance is
refused in 7 of 7, and a star target from outside is refused in 7 of 7. Both scenarios are
constructible and true. The service-level path was read, not run.

**(c) The pinned copy.** It is the writer's own, and it is now testable, which was the
finding. The origin line's "right now" satisfies the reliability note; the destination line is
the existing one, as ruled. One observation for whoever owns copy, not a finding: "That body is
no longer in this system" asserts the body was once there, which is false for an id that never
existed (a direct request or the agent's passthrough). It is harmless and the line is pinned in
one place.

## MINOR 1 — task 1.4's id search does not guarantee the two wrong wirings from BLOCKER 1 are caught

**Evidence.** `tasks.md` 1.4: "choosing the system id by search so the derived parent is the
wanted body". The two scenarios constrain only which body the derivation names. The parent index
is `mix64(mix64(SystemSeed(seed, id))) % len(Bodies)` (`station_continuous.go:30,42`).

**Exploit.** With a two-body skeleton, an implementation that passes seed 0 computes the same
index as the real seed for about half of all ids, so an id found by the stated search lets that
implementation pass both directions about one time in four. An implementation that always reads
`Bodies[0]` passes both directions if the SDET realises the two directions by swapping body
order under one id, since the derived index is then 0 in both. The scenarios are right; the
arrangement is one clause short of forcing the failure.

**What a fix must achieve.** The search in 1.4 must also require that, for each chosen id, the
index derived under the document's seed differs from the index derived under seed 0, and that
the derived index is non-zero in at least one of the two directions. No scenario text needs to
change.
