Reliability review — `fix-world-time-render-loop`, Phase 1. Read-only; findings and paste-ready text below for the spec writer.

## Ruling on the central evidential question

The ADDED requirement's core clause — "the view SHALL NOT be the reason a requested navigation fails to arrive" — is sound **as an invariant** even though design.md admits the causal mechanism (why React's ~5s transition-expiry rescue didn't fire) is unverified. What makes it sound: the requirement is phrased as an outcome ("SHALL commit"), not as an assertion of the mechanism ("because the transition lane never expires"); the discriminating experiment (4/6 stall with the per-frame `setState`, 0/6 with it silenced, same spec, same six repeats) isolates the *causal factor* (the per-frame update) even though it doesn't explain React's internal scheduling. Design.md's own risk mitigation — "the gate is empirical: repeat-6 green and zero diagnostics… if it is not green after this change, the diagnosis was incomplete — stop and re-measure, do not tune" — is the correct posture: it treats the fix as a falsifiable hypothesis with a pre-committed stop condition, not as a tuned-until-green result. What is missing (findings 8–9 below) is that the *sample size* backing both the diagnosis and the closing gate is too small to treat a green run as confirmation, and that the *unit-level* evidence proposed alongside it cannot exercise the mechanism at all. Those are the actual gaps — not the causal story being incomplete.

## Findings

**1 — BLOCKER — `clock.now()` has no specified behavior before the first served reading, and it runs inside an animation-frame callback that no React boundary can catch**
Evidence: design.md:55–58, `frontend/hooks/use-world-time.ts:56,61-64,69-70` (old code guards with `if (anchor.current)` and never calls `projectWorldTime` before the first re-anchor — `worldTime` state simply stays at its initial `serverWorldTime ?? 0`, so `buildSceneModel` is *always* called with a defined number). design.md's `createWorldClock()`/`now()` is "`projectWorldTime`… moved here verbatim" with no stated guard, and tasks.md 3.1–3.3 don't test the pre-anchor case. `projectWorldTime(anchor, wallNow, scale)` destructures `anchor.world`/`anchor.wall` — if `anchor` starts `null` and `now()` is called before `anchor()` ever runs (exactly the state the view is in for at least one frame after mount, before the interior/fleet read lands), this throws. Per the live spec (`system-space-view/spec.md:1023-1030`, 1132 area), an error "thrown inside… an animation-frame callback… is not reachable by a React error boundary at any placement" — so this would surface as an uncaught exception, not a contained "unsupported" state, directly undermining *Renderer Unavailability Is an Explicit State* and *Lost Rendering Context Recovers Without Navigation*'s containment guarantees.
Why it matters: this is exactly the class of bug the old architecture structurally couldn't have (worldTime was always a defined number from mount). The new architecture can reintroduce it silently unless the pre-reading case is explicit.
Proposed text (design.md, Decision 1, appended):
> `now()` before the first `anchor()` call SHALL return the value implied by "no reading yet" without throwing — the clock has no anchor to project from, so `now()` SHALL return `0` (matching the deleted hook's initial `serverWorldTime ?? 0` state) rather than projecting against an uninitialized anchor. `hasReading()` distinguishes this state for any caller that needs to skip work rather than render at `0`.
Proposed task (tasks.md, section 3):
> - [ ] 3.6 Unit test: `clock.now()` called before any `anchor()` call returns `0` and does not throw; a frame loop that calls `buildSceneModel({..., worldTimeMs: clock.now()})` before the first served reading renders without error.

**2 — BLOCKER — Design.md's proposed test coverage for the frame-loop position system cannot be built as described; confirmed by the test harness, not inferred**
Evidence: `frontend/components/space/webgl/SpaceWorld.tsx:27-30` ("Under jsdom… it mounts, finds it cannot draw, and returns without throwing") and the actual guard at `SpaceWorld.tsx:220-221` (`if (!probe || typeof probe.createProgram !== 'function') return`). `frontend/vitest.setup.ts:134-138`'s `fakeWebglContext()` implements **only** `getExtension` — no `createProgram` — and its own comment states: "No production module in this change constructs a real `THREE.WebGLRenderer` against it." That stub exists solely to satisfy `render-guard/probe.ts`'s *availability* check, a different code path from `SpaceWorld`'s renderer construction. Consequence, confirmed by inspection: `draw()` (SpaceWorld.tsx:627) **never executes under any current vitest test** — every `SpaceStage`/`SpaceWorld` test today exercises the "unsupported" fail-soft branch, never the live draw loop.
Design.md Risk #2 (design.md:148-151) says: "Position assertions move to a pure `projectMarks(scene, basis)` unit; **component tests assert registration and that a frame writes a transform**." That second clause is not buildable under the current test infra: if `draw()` never runs under jsdom, no component test can observe a written transform. This also means the entire relocated per-frame system this change's "expensive half" is built around — `buildSceneModel` running inside the loop, the `Map<markId, HTMLElement>` registry, `projectMarks` actually being *called* against live inputs, `pickAt` reading the frame loop's latest marks — ships with **zero automated coverage** beyond the decontextualized pure-function test of `projectMarks` and the tier-4 journey's navigation/console-error assertions (which say nothing about hit-target correctness, registration, or leak-freedom).
Why it matters: this is a testability gap being designed in, not discovered later — exactly the "built and never called" shape Lesson One warns about, except here it's "built and never *test*-called."
Proposed fix (pick one, state the choice in design.md before tasks are written):
> (a) Extend `vitest.setup.ts`'s fake WebGL context with the minimum THREE.js needs to construct a renderer (`createProgram`, `createShader`, `createBuffer`, `getParameter`, etc. — a known, bounded surface used by several open-source THREE/jsdom test setups), and add a task asserting `draw()` runs and writes a `style.transform`; or
> (b) extract the DOM-transform-write responsibility (registry lookup + `projectMarks` + `el.style.transform = …`) into a function that does not require a live `THREE.WebGLRenderer` to exist, callable and testable independent of GL construction (its own `requestAnimationFrame` loop, gated on `available` the same way `draw()` is, but not gated on `renderer` construction succeeding). Add the corresponding task and test either way — tasks.md currently has neither.

**3 — MAJOR — The `Map<markId, HTMLElement>` registry has no specified de-registration path**
Evidence: tasks.md 4.3 ("SpaceLayers registers each mark element by id; `draw()` writes `style.transform`… after `renderer.render`. No element is keyed on position.") names registration but not un-registration. Marks that come and go over a session — sightings (`add-scan-and-sightings-surface`), contacts, transient fleets entering/leaving the system — will have their DOM elements removed by React when they drop out of the coarse-rendered mark set. If registration is a plain `useRef(new Map())` populated on mount rather than a callback ref (`ref={(el) => { el ? map.set(id, el) : map.delete(id) }}`), the map retains references to detached nodes for the life of the view, an unbounded-per-session memory leak, and `draw()` continues doing pointless work writing transforms to dead elements every frame.
Why it matters: this is the concrete "registry holding detached elements after a re-render removes marks" hazard called out in the task brief, and per Finding 2 it has no test path that would catch it if built wrong.
Proposed task (tasks.md, section 4):
> - [ ] 4.3a Registration uses a callback ref (`el ? registry.set(id, el) : registry.delete(id)`), never a mount-only effect. Test: a mark present for several coarse renders then absent (a sighting expiring, a contact leaving range) is removed from the registry within one render — assert via a spy/counter on the registry's size, not by inspecting `draw()` (which per Finding 2 may not run under jsdom).

**4 — MAJOR — "on the order of once per elapsed second" is an adjective, not a threshold**
Evidence: `openspec/changes/fix-world-time-render-loop/specs/system-space-view/spec.md:42` ("the view rendered on the order of once per elapsed second, not once per animation frame"). Tasks.md 2.2 already has a concrete number ("render count grew by ≤3") that the requirement text doesn't state. "On the order of" gives no pass/fail line — is 5 renders over 2 elapsed seconds a violation? The requirement should carry the same number the test enforces.
Proposed text (replace the scenario's THEN clause):
> #### Scenario: A counting figure advances without a per-frame render
> - **GIVEN** the acting fleet is burning with a served arrival in the future
> - **WHEN** two wall-clock seconds elapse with no read landing
> - **THEN** the figure counting down to that arrival has changed
> - **AND** the view has rendered no more than 3 times in that interval — bounded independent of the animation-frame rate, not scaling with it

**5 — MAJOR — Decision 2's refetch-accuracy argument does not cover the display-flip lag it also concedes**
Evidence: design.md:86-91 ("State flips gated on time (`mineRunning`, `ScanControl`'s `settling`, `rosterCommandVisibility`) may now land up to 1s after the served instant… Accepted: every one of them is already followed by an ETA-scheduled refetch… that ref is replaced by `clock.now()`, so scheduling gets more accurate, not less."). Traced against the code: the *scheduling* claim is correct and verified — `SystemSpaceView.tsx:508-518` (the ETA-effect that arms `setTimeout`) and `:595` (the mine-landed check) both run inside `useEffect`s keyed on data changes, not on every frame, and per tasks.md 3.3 the `worldTimeRef.current` reads there become direct `clock.now()` calls — a **more** precise one-time snapshot than the ref ever was. That is real and correctly justifies the *refetch timing*.
But `mineRunning` at `SystemSpaceView.tsx:693` (`!!runningMine && runningMine.eta > worldTime`) and `settling` in `ScanControl.tsx:179` (`runningEta !== null && runningEta <= worldTime`) are **not** ref reads inside an effect — they're plain expressions evaluated at render time against the `worldTime` **prop**, which per design.md:80-84 becomes the coarse (1 Hz) value. The refetch-accuracy argument is about a different code path; it says nothing about why a boolean gate re-evaluated once per second instead of once per ~16 ms is fine on its own terms. Likewise `FleetRoster.tsx:122-135`'s own comment — "`worldTime` re-arms the sweep every tick, so a label/gate lifts at eta without waiting for a cache event" — documents that `rosterCommandVisibility`'s responsiveness is *directly* a function of the `worldTime` prop's cadence, which this change reduces ~60×.
No live requirement states a freshness bound for these flips (`fleet-roster/spec.md:66-71,106-111` says only "at or before the current world time," no cadence), so this is not a spec violation — but it is exactly the "adjective in disguise" the reliability lens is built to catch, and Decision 2's stated justification doesn't actually reach it.
Proposed text (design.md Decision 2, append a paragraph):
> The refetch-scheduling argument above covers only the self-scheduled `setTimeout` calls, which read `clock.now()` at arm-time and are unaffected by tick cadence. It does not cover `mineRunning`, `ScanControl`'s `settling`, or `rosterCommandVisibility`'s gate-lift, which are plain per-render comparisons against the `worldTime` prop and will lag the served instant by up to 1s under the coarse tick where they previously lagged by ≤16ms. Accepted separately: no requirement in `system-space-view`, `fleet-roster`, or `focused-scan` states a freshness bound tighter than "at or before the current world time," and `figure-formatting`'s own duration text has no sub-second resolution, so a 1s lag in a *state flip* that gates a control's presence is a genuine, if minor, UX regression, not a spec violation.

**6 — MAJOR — `galaxy-view` shares the identical starvation mechanism, gets no requirement delta, and has zero test coverage of it, before or after**
Evidence: `GalaxyView.tsx:182` (`useWorldTime(myFleets?.[0]?.worldTime ?? galaxy?.worldTime)` — no `scale`, its own separate gap, see Finding 12) drives a per-frame `setState` exactly like `SystemSpaceView`'s, forcing the whole tree — including its own `router.push` call sites at `GalaxyView.tsx:245` (drill-in navigation) and `:281` (roster cross-nav) — to re-render ~60×/s. The `worldTime` value itself is consumed only by `FleetRoster` (`GalaxyView.tsx:473`) for countdown/gate cadence — the GL graph (`GalaxyGraph.tsx`, its own rAF loop) doesn't take it — so this is the *exact same shape* of bug: a per-frame render whose only payload is a once-a-second-adequate figure, sitting upstream of a `router.push`. `GalaxyView.test.tsx:163` mocks `useWorldTime` to a constant `0`, so no unit test today, or proposed by tasks.md 3.4 ("same swap; update `GalaxyView.test.tsx`'s mock"), exercises real per-frame churn interacting with a real navigation in this view. Proposal.md:53 states "`galaxy-view` takes no delta: no requirement of it names the clock's cadence, and its observable behaviour does not change" — true at the requirement-text level, but the underlying invariant this change exists to establish ("animation never starves a navigation") is being fixed in `galaxy-view`'s code with no requirement anchoring it there and no proposed test verifying it.
Why it matters: a future regression in `GalaxyView` (someone reintroducing a per-frame `setState`) would not be caught by anything this change adds, because the invariant lives only in `system-space-view`'s spec.
Proposed text (either add to `galaxy-view/spec.md` or explicitly scope out with rationale — recommend the former, minimal delta):
> ### Requirement: Animation Never Starves Drill-In or Cross-System Navigation
> The system SHALL NOT let the passage of an animation frame cause a per-frame render of the galaxy view's component tree; a drill-in navigation to a system's space view (*Drill-In Navigation to the System Board*) and a roster's cross-system fleet selection issued from a mounted, animating galaxy view SHALL commit.
>
> #### Scenario: A drill-in navigation made while the view animates arrives
> - **GIVEN** the galaxy view is mounted and animating
> - **WHEN** a system is chosen for drill-in navigation
> - **THEN** the browser arrives at that system's space-view route
Proposed task (tasks.md, section 3):
> - [ ] 3.4a `GalaxyView` render-count test: fake timers, advance several rAF frames with no other event → render count unchanged; a drill-in click and a cross-system roster selection each still call `router.push` (real `next/navigation`, not the existing mock, or a spy that distinguishes commit from call).

**7 — MAJOR — Off-screen reach-chip membership can lag actual on/off-screen state by up to 1s, creating a brief window where a mark is reachable by neither path**
Evidence: design.md:114-116 ("Membership that depends on position — the off-screen reach chips, a burn mark appearing/disappearing — is recomputed at the coarse cadence and on camera change. A chip may lag a body crossing the viewport edge by up to 1 s."). Live requirement `system-space-view/spec.md:1709-1722` ("Off-Screen Bodies and Lane Gates Are Reachable by Pointer and Touch") uses "currently lies outside the viewport" with no freshness qualifier. Per Decision 3, the DOM hit target's *position* is still moved every frame by the draw loop (so it can genuinely leave the viewport bounds between coarse renders), while the *chip* that would let the player reach it once it's off-screen only appears at the next coarse tick or camera change. In the window between a body's mark leaving the viewport and the next coarse recompute, the mark is neither clickable via its ordinary hit target (it's off-screen) nor covered by the affordance (hasn't appeared yet) — bounded to ≤1s and only when a body's own motion (not camera motion) crosses the edge, but a real, inducible gap.
Proposed text (system-space-view/spec.md, append to *Off-Screen Bodies and Lane Gates Are Reachable by Pointer and Touch*):
> The affordance's membership SHALL be recomputed at least once per wall-clock second and on every camera change, so a mark crossing the viewport edge by its own motion is covered by the affordance within one second of leaving the viewport, never left reachable by neither the ordinary hit target nor the affordance for longer than that.
>
> #### Scenario: A mark that leaves the viewport under its own motion gains the affordance within a second
> - **GIVEN** a body or lane gate inside the viewport, moving under world time alone with no camera change
> - **WHEN** its position crosses the viewport edge
> - **THEN** its off-screen affordance is offered within one wall-clock second of that crossing

**8 — MAJOR — Both the diagnosing experiment and the proposed closing gate are statistically underpowered against the observed base rate**
Evidence: `defect-cross-system-chevron-nav-stall.md:18-22` — base rate 4/6 stalling (67%) pre-fix; the discriminating ablation 0/6 stalling with the tick silenced; tasks.md 5.3 proposes closing on `--repeat-each 6` again. A 0-of-6 result is weak evidence of a true near-zero failure rate: if the real post-fix failure rate were, say, 15% (a plausible residual given the mechanism is admittedly not fully understood), P(0 failures in 6 trials) ≈ 0.85⁶ ≈ 38% — i.e., a coin-flip-adjacent chance of seeing exactly this "clean" result even with meaningful residual risk. The Clopper-Pearson 95% upper bound on a true failure rate given 0/6 successes is roughly 39%. Six repeats cannot distinguish "fixed" from "meaningfully still broken" at any usable confidence, for either the diagnostic experiment or the closing gate.
Why it matters: this is the closing evidence for a defect literally about a race condition whose full mechanism is unverified — exactly the situation calling for more power, not less.
Proposed task (tasks.md, replace 5.3):
> - [ ] 5.3 Tier 4, quiet machine: `bash scripts/dev/with-test-emulators.sh 'cd frontend && npx playwright test e2e/tests/vitals-strip-journey.spec.ts --repeat-each 20'` — 20/20 past the cross-system `waitForURL`, zero `Maximum update depth` lines in `[journey-console]`. Run this twice, on separate invocations (not one `--repeat-each 40`), before recording the defect CLOSED — a single run's 20/20 has a 95% upper-bound failure rate around 14%; two independent 20/20 runs tightens that meaningfully and rules out a machine-state confound. This is the CLOSING run's repeat count, not the standing per-change tier-4 default — record the rationale in `fix-world-time-render-loop-journey.md` so it isn't read as a new default.

**9 — MAJOR — The proposed fake-timer unit tests are structurally incapable of exercising the actual defect (confirmed, not hypothesized)**
Evidence: design.md Decision 5 proposes a `React.Profiler`/render-count probe under fake timers as primary evidence alongside the journey. `frontend/components/space/SystemSpaceView.test.tsx:37` mocks `next/navigation` entirely (`vi.mock('next/navigation', () => ({ ... }))`) — confirmed by grep, no `useWorldTime` mock exists in this file (the real clock hook runs). This means: the render-churn *is* real in these unit tests, but `router.push` is a bare mock function call, not a real React transition — a mock cannot be "interrupted" by scheduler priority because it never enters React's scheduler at all. **No unit test in this codebase's current architecture — mocked or not — can ever observe the actual failure mode** (a real App Router transition starved by a real per-frame render), because doing so requires the real `next/navigation` router under a real Next server, which only the tier-4 Playwright journey provides. This is Lesson Two's exact concern, and here it's provable rather than inferred: even a *maximally faithful* fake-timer unit test (real clock, real component tree, real render counting) cannot touch the transition-starvation mechanism, because the one thing that mechanism depends on is mocked out by necessity.
Why it matters: design.md doesn't currently say this explicitly, so a future reader could mistake "render count unchanged" (Group 2's unit tests) for evidence that navigation is fixed. They are not the same claim.
Proposed text (design.md, Decision 5, append):
> The unit-level render-count and update-depth tests are regression guards for the *mechanism this change removes* (a per-frame `setState`) — they are necessary but not sufficient evidence for *Animation Never Starves a Navigation*'s central claim. `SystemSpaceView.test.tsx` mocks `next/navigation`, so no unit test — under this change or any future one — can exercise a real App Router transition; only the tier-4 journey, against a real dev server, tests whether a navigation actually arrives. Treat a green unit suite alone as proof of nothing about navigation; the journey is the only evidence for that clause.

**10 — MAJOR — Shared, single-run acceptance evidence between two changes compounds Finding 8's statistical weakness**
Evidence: design.md:161-165 ("Land and archive before re-running `add-vitals-strip`'s archive gate; that gate's journey is this change's tier-4 evidence, so one quiet-machine run serves both."). Combined with Finding 8: if the one shared run happens to land green by chance against a residual (non-zero) failure rate, **both** `fix-world-time-render-loop`'s closure **and** `add-vitals-strip`'s archive are granted off a single data point, and the residual risk becomes invisible to both changes' records simultaneously — there is no second, independent check that would catch a lucky pass.
Proposed text (design.md, Migration Plan, replace the sharing sentence):
> Land and gate this change on its own tier-4 run(s) first (Finding 8's repeat count), record the defect CLOSED in `defect-cross-system-chevron-nav-stall.md` against that evidence alone, and only then re-run `add-vitals-strip`'s archive gate as a **separate** invocation. The two changes' acceptance evidence must not be the same process execution, even though they exercise the same spec file, so a one-off pass on a quiet machine cannot silently clear both records at once.

**11 — MAJOR — Rollback plan doesn't address the post-archive case**
Evidence: design.md:162 ("Rollback is `git revert`.") Tasks.md 5.6 archives this change (folding the ADDED requirement into `openspec/specs/system-space-view/spec.md`) and then re-runs `add-vitals-strip`'s gate, presumably archiving that too. If a defect is later found that requires reverting this change's *code*, a plain `git revert` leaves the archived spec text (*Animation Never Re-Renders the View, and Never Starves a Navigation*) asserting an invariant the reverted code no longer holds — a spec/code divergence that `git revert` alone does not surface or correct. It also silently re-opens `add-vitals-strip`'s original blocker without any note that its archived status is now suspect.
Proposed text (design.md, Migration Plan, append):
> If a revert is needed **after** this change has archived, `git revert` alone is insufficient: the ADDED requirement in `openspec/specs/system-space-view/spec.md` must be reverted or reopened as its own change alongside the code, and `docs/plans/continous_space/handoffs/defect-cross-system-chevron-nav-stall.md` must be reopened (status back to OPEN) — a code-only revert would leave the spec asserting an invariant the code no longer holds, and `add-vitals-strip`'s archived status must be reconsidered since its own gate depended on this fix.

**12 — MINOR — `GalaxyView`'s clock has never been given a served scale (pre-existing, adjacent to this change)**
Evidence: `GalaxyView.tsx:182` — `useWorldTime(myFleets?.[0]?.worldTime ?? galaxy?.worldTime)`, no `scale` argument, defaulting to 1 inside the hook. Not introduced by this change, and not in scope per the proposal, but task 3.4 ("GalaxyView: same swap") is a natural point to note or fix it, since a world running at a non-1 scale would make every countdown in the galaxy-view roster wrong today and after. Flagging as an aside, not a blocking finding.

**13 — MINOR — `reducedMotion` is hardcoded `false` in `SystemSpaceView` (pre-existing, adjacent to the MODIFIED requirement)**
Evidence: `SystemSpaceView.tsx:438` (`reducedMotion: false` passed unconditionally to `buildSceneModel`). Design.md's Non-Goals explicitly state reduced-motion behavior is unchanged, which is true of the *code path* — but the MODIFIED requirement's restated focus-retention clause ("as the view animates") is not actually reachable under a real reduced-motion preference today, because the preference is never read from `matchMedia`. Not this change's defect to fix, but per this project's own standing lesson ("treat every 'X is unaffected' as a hypothesis," quoted in the brief for this exact weak point), this should be recorded as a known gap rather than silently assumed fine. No text change proposed; recommend a one-line note in design.md's Non-Goals: "Reduced-motion is unchanged and, independently of this change, not yet wired to the OS preference (`reducedMotion: false` is hardcoded at `SystemSpaceView.tsx:438`) — out of scope here."

**14 — MINOR — Timer/anchor atomicity and visibility-driven resync are unaddressed**
Evidence: design.md:61-64 doesn't specify whether `anchor()` assigns a new anchor object (`this.anchor = {world, wall}`) or mutates fields in place; the latter is more failure-prone if the clock object is ever read concurrently with a mutation (e.g., via a future `useSyncExternalStore` consumer). Low risk given JS's single-threaded execution, but cheap to specify.
Proposed text (design.md, Decision 1, append): "`anchor()` SHALL replace the clock's anchor with a new object in a single assignment, never mutate the previous anchor's fields in place."

**15 — MAJOR — No `visibilitychange` handling; the 1 Hz requirement's literal wording is falsifiable by ordinary browser tab-backgrounding**
Evidence: `useCoarseWorldTime(clock)` is a plain `setInterval(fn, 1000)` (design.md:79-80). Chrome and other browsers apply "intensive throttling" to background-tab timers after ~5 minutes hidden, reducing effective `setInterval` cadence to roughly once per minute unless the page holds an exemption (audio, WebRTC, etc.) — none of which applies here. The ADDED requirement's literal text ("Every figure this view presents that counts in time… SHALL update at least once per wall-clock second") has no visibility qualifier and would be false whenever the tab is backgrounded long enough. Separately, `SpaceWorld`'s `draw()` (rAF-based) has *always* paused when hidden — that part is unchanged and not a regression; what's new is that the *coarse tick* (interval-based) does not share that pause, so the two clocks the view now depends on (frame loop, coarse tick) diverge in background-tab behavior in a way the single old 60Hz-`setState` loop didn't. This is inconsequential while genuinely hidden (nobody sees the DOM), but the requirement as written makes no such carve-out, and no task addresses re-syncing on foreground return (though the design's read-on-demand `clock.now()` model means a correct value appears the instant *any* tick fires again, so no stale-value bug — just an unstated exception to a literal "at least once per second" claim).
Proposed text (system-space-view/spec.md delta, add a qualifier to the ADDED requirement's second paragraph):
> …SHALL update at least once per wall-clock second **while the document is visible** and SHALL NOT require a per-frame render to do so. While the document is hidden, this figure MAY update at a reduced cadence subject to the browser's own background-timer policy; on the document becoming visible again, it SHALL reflect the current world time within one wall-clock second, never a value frozen from before the hidden interval.
>
> #### Scenario: A figure resyncs promptly when the tab regains visibility
> - **GIVEN** the space view was hidden (backgrounded) for longer than its coarse tick's interval
> - **WHEN** the document becomes visible again
> - **THEN** every counting figure reflects the current world time within one wall-clock second, not a value computed from before the tab was hidden

But task 4.7 ("Migrate the assertions counted in 1.1… every moved assertion keeps its scenario name") bundles an as-yet-uncounted amount of work from five existing test files (design.md:142-143: "`SpaceStage` is 1034 lines with five test files asserting mark positions through render"). No text change proposed; flagging so the count from 1.1 is actually checked against the cap before task 4 is expanded into real subtasks, per the seam design.md already describes.

## The brief's flagged weak points — ruled

- **"Frames pass without the view rendering" / "on the order of once per elapsed second" testability and altitude** — testable (via `React.Profiler`/render-count probe and a `data-draw-world-time` DOM read, both standard techniques); altitude is *consistent with existing repo precedent* (the live spec already names "React error boundary," "re-render," and has an existing scenario using "re-renders" verbatim at `system-space-view/spec.md:1274`), so not a convention violation — but "on the order of" is a genuine threshold gap (Finding 4).
- **Requirement soundness given the unverified mechanism** — ruled sound above; the requirement is an outcome invariant, not a claim about React internals, and the design's own "stop and re-measure, don't tune" fallback is the correct posture. The gap is evidential power (Findings 8–9), not requirement soundness.
- **1Hz lag on `mineRunning`/`settling`/`rosterCommandVisibility`** — **founded**, traced to specific code (`SystemSpaceView.tsx:693`, `ScanControl.tsx:179`, `FleetRoster.tsx:122-135`) and confirmed *not* covered by Decision 2's stated justification, which addresses a different code path (Finding 5). No existing requirement is violated (no cadence bound exists), but it needs its own accepted-trade-off text rather than riding on an argument that doesn't reach it.
- **Off-screen reach chips vs. coarse cadence** — **founded**, a real (if narrow, ≤1s) reachability gap (Finding 7).
- **Picking against the frame loop's marks** — **cleared**. Task 4.4 ("`pickAt` reads the frame loop's latest marks from a ref, not the last render's") directly targets the requirement's need (*Space View Picking Resolves to the Body, Lane Gate, or Point Under the Pointer*'s "Hit targets SHALL be positioned at the marks actually drawn"); the design's plan is correctly shaped for it, though per Finding 2 it currently has no automated test path to confirm the implementation matches the plan.
- **Reduced-motion and lost-context claims of "no delta needed"** — reduced motion: **founded as a pre-existing gap, not one this change introduces or need fix** (Finding 13) — the requirement (`system-space-view/spec.md:1323-1328`) is about decorative freezing with positions still advancing, which is architecturally orthogonal to where world time lives (state vs. clock object) and unaffected either way; but `reducedMotion: false` is hardcoded, so the requirement isn't reachable today regardless. Lost-context: **cleared** — traced against `system-space-view/spec.md:1132-1198`, Decision 3's "the first post-restore frame stamps `clock.now()`" and task 4.5's explicit re-pointing of the restore test directly satisfy *A restored context's first frame reflects live state*; Decision 4's "no change to the unavailability requirements" is also **cleared** for the data-draw-world-time freeze behavior specifically (it was *already* guarded by `if (!available) return` in the old `SpaceStage.tsx:201` effect — this is unchanged, not new), though hit-target *movement* becoming coupled to canvas availability is a genuine (benign) behavior delta worth one documentation line, since selection via canvas is already fully blocked in that state by the existing requirement (*Renderer Unavailability Is an Explicit State*'s "Burn target selection is unreachable without the canvas").
- **Whether `galaxy-view` really needs no delta** — **founded, not cleared** (Finding 6): true at the requirement-text level (no scenario names cadence), but the identical starvation mechanism is present and fixed in code with zero requirement anchor and zero proposed test.
- **Task sizing against the 40-task cap** — **process is sound, not yet validated** (Finding 16): task 1.1 is the right mechanism, hasn't run yet.
- **`system-console`/`add-vitals-strip` semantic collision** — **cleared**. Traced `add-vitals-strip/specs/system-console/spec.md:341-345` ("The countdown advances between reads") and `:636` ("The stamp advances between reads") against `VitalsStripFleetCell`'s actual contract (`VitalsStripFleetCell.test.tsx:20,35,52`): the pill is a pure function of a `worldTime` **prop** supplied by its parent, with no cadence assumption baked into the component or its tests — feeding it a coarser-updating prop changes update *frequency*, not the *relationship under test* ("value changed → text changed"). No scenario in either change's delta asserts sub-second timing. **Ruling on archive order**: not because of a text collision (none found — all six shared scenario headings in the MODIFIED *Body, Lane-Gate, and Point Selection Is Keyboard-Operable* delta are verbatim-preserved against the baseline, checked line-by-line), but because `add-vitals-strip`'s own archive gate is blocked by the exact defect `fix-world-time-render-loop` fixes: `fix-world-time-render-loop` must land, pass its own (separately-run, per Finding 10) tier-4 evidence, and archive **before** `add-vitals-strip`'s archive gate is re-run.

## Verdict

**NEEDS FAILURE SPECS.** The requirement's central invariant is well-formed and the overall architectural direction (clock-object-not-state, frame loop owns the picture) is sound and correctly scoped against `space-kinematics`'s render-only permission. But two BLOCKER-level gaps (undefined pre-reading clock behavior escaping error-boundary containment; a test-coverage plan for the frame-loop position system that the test harness cannot currently execute as described) and a cluster of MAJOR gaps (adjective thresholds, an unaddressed display-flip lag, `galaxy-view`'s untested identical exposure, off-screen reachability's narrow gap, underpowered closing evidence, unit tests structurally unable to touch the real defect, shared single-run acceptance risk, and a rollback plan silent on the post-archive case) need text added to design.md, the spec delta, and tasks.md before this proceeds past Phase 1.
