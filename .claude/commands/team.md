Launch the OpenSpec spec-driven development team on: $ARGUMENTS

You are the entry point for the OpenSpec agent team. Delegate the work to the `openspec-orchestrator` agent via the Agent tool — do not run the pipeline yourself in this session. The orchestrator coordinates: entry-mode routing (brownfield/greenfield/specced), design analysis, spec authoring, the specialist review panel, validation, adversarial review, and (only when implementation is requested) the TDD implementation crew.

## Interpret the arguments

- **A file path** (design doc, PRD, brief): the source document for a design-to-spec run. Verify the file exists before delegating; if it doesn't, tell the user instead of launching. A path that is a **chain doc** (a links table of change-ids with states — `docs/plans/<chain>/chain.md` by convention) is a `--chain` run even without the flag: `/team docs/plans/x/chain.md --full-auto` means `--chain docs/plans/x/chain.md --full-auto`.
- **Free text**: treat as a feature request / mini design brief; pass it verbatim. This includes "quick fix" and bug-report phrasing — the team never edits code directly; small requests become fast-tracked minimal changes (writer → validator → adversary) and are implemented from the change, so set that expectation when relaying results.
- **An existing change-id** (matches a folder in `openspec/changes/`): resume work on that change — the orchestrator should assess its state (validated? reviewed? implemented?) and continue from the right stage. Remind it that a resumed change whose content has no CURRENT adversary verdict gets adversarial review before anything else proceeds — prior verdicts expire on edit.
- **`--implement`**: authorize end-to-end delivery (Phase 2 after Phase 1) without a second approval gate. WITHOUT this flag the orchestrator must stop after presenting the validated spec.
- **`--brownfield <capabilities>`**: start with a baseline retrofit of the named capabilities via `openspec-brownfield` before any change is authored.
- **`--greenfield`**: force the net-new bootstrap path via `openspec-greenfield` (also inferable when no code and no `openspec/` exist).
- **`--chain <chain doc>`**: implement a sequence of already-authored changes in archive order, one link at a time. Verify the chain doc exists (`docs/plans/<chain>/chain.md` by convention; its table lists change-ids and states). Optional `--from <change-id>` starts at that link; otherwise start at the first link whose state is not archived. Run the links **sequentially, one fresh orchestrator per link** — never one orchestrator carrying every link — and update the chain doc's state column with the archive commit before moving on. Each per-link delegation is the resume form below with Phase 2 authorized, plus these three instructions: (1) before implementing, confirm the link's adversary verdict is current by diff against the commit recorded in `docs/plans/continous_space/handoffs/<id>-adversary-r<N>.md`, and re-attack only the diff if not; (2) the archive gate is the single journey run per `docs/testing-tiers.md`; (3) write what the link taught into the chain doc's per-link section. Stop the chain and report at the first link whose gate cannot be evaluated or whose journey stays red after its one batched revision round. Without `--full-auto`, a link whose state is `not authored` (no `openspec/changes/<id>/` folder) also stops the chain — say so and name the flag. With `--workflow`, pass `chain: <path>` (and `from`) to the Workflow instead.
- **`--full-auto`**: lift every user gate and run to archive without stopping to ask. With `--chain`, a `not authored` link is **authored in-run** before it is built: that link's delegation is the *author* form — the design input is the chain doc path (its table row for the link, its open-decisions section, the "taught" records of the archived links before it, and every source document it names for that link), entry mode specced against the archived predecessors' specs, Phase 2 authorized — and the orchestrator runs the full Phase 1 (analyst → writer → panel → validator → adversary loop), then commits the change folder and handoffs, records that commit as the verdict commit in the latest `docs/plans/continous_space/handoffs/<id>-adversary-r<N>.md`, sets the chain doc state to `authored r<N> <hash>`, and only then runs the currency check and build. Open questions are **ruled in-run, not asked**, by this precedence: the chain doc's or design input's recorded recommendation; then a settled decision in the root `CLAUDE.md` / `openspec/project.md`; then the panel's recommendation; then the most reversible option (one migration, one flag, or one file to undo, no backfill). Every ruling is a `FULL-AUTO RULING` entry in `docs/plans/continous_space/handoffs/<id>-rulings.md` with its basis, the alternatives rejected, and the reversal cost, and every one is listed in the report. A question that needs information nobody in the repo has — a credential, an external account, a product call with no recorded lean — is a **hard stop**, never a guess. The size cap still applies: a link past 40 tasks splits at its pre-identified seam and the second half's row is inserted after it in the chain doc, state `authored`. Nothing else changes — the adversary is still non-skippable, TDD still holds, the archive gate is still the single journey run, and the chain still stops at the first hard stop, BLOCKER residue at the round cap, or gate that cannot be evaluated or stays red. Without `--chain`, `--full-auto` is `--implement` plus the in-run rulings (and, on the greenfield path, the MVP line is drawn from the design input's stated scope and recorded rather than confirmed). With `--workflow`, pass `fullAuto: true`.
- **`--workflow`**: run the deterministic multi-agent pipeline instead of a single orchestrator agent — invoke the Workflow tool with `{name: "openspec-team", args: {...}}` (this flag is your authorization to call Workflow). Map the other arguments into workflow args: `designDoc` (resolved path), `request` (free text), `changeId`, `implement: true` for `--implement`, `fullAuto: true` for `--full-auto` (implies implement, and archive when a chain is passed), `entryMode: "brownfield"` + `capabilities: [...]` for `--brownfield`, `entryMode: "greenfield"` for `--greenfield`. The workflow never archives unless `archive: true` (or a chain) is passed — only add it if the user explicitly asks to archive. The workflow runs in the background; relay its returned report (entryMode, changeIds, harden status, open questions, implementation results) when it completes.
- **No arguments at all**: don't guess. Report the current state (is the `openspec` CLI installed — `openspec --version`? does `openspec/` exist? active changes via `openspec list` or the changes/ folder? obvious design docs in the repo?) and ask the user what to run. A missing CLI is not a blocker to mention as one — the team installs it as part of any run.

## Delegation

Spawn `openspec-orchestrator` (Agent tool, subagent_type `openspec-orchestrator`) with a prompt containing:

1. The user's request verbatim, plus resolved file paths (never summarize a design doc — pass the path)
2. The entry-mode signal you inferred or the user forced (brownfield/greenfield/specced), with your evidence
3. Whether Phase 2 is authorized (`--implement`, `--full-auto`, or a chain link) or the run stops at the validated spec — and, under `--full-auto`, that every user gate is lifted and the ruling and hard-stop rules above apply
4. The reminder that its final report must include: change-id(s), file tree created, validation status, findings resolved vs. open questions, and Phase 2 results if run
5. The reminder that its durable state is `docs/plans/continous_space/handoffs/` (per `docs/plans/continous_space/handoffs/README.md`) and its test commands come from `docs/testing-tiers.md` — the prompt itself carries neither findings text nor suite commands

When the orchestrator returns, relay its report to the user faithfully — including open questions and unresolved findings, not just the successes.
