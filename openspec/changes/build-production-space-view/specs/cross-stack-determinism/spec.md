## MODIFIED Requirements

### Requirement: Shared Board Math Is Pinned By a Cross-Language Golden Fixture
A function that computes a rule-bearing value and is implemented in both a Go package and a TypeScript module SHALL be covered by a cross-language golden fixture file; where no such file exists for that package pair, the change introducing the mirror SHALL create one. A rule-bearing Go package that computes persisted values, solve results, or ETAs, and that a change deliberately builds with no TypeScript mirror at all, SHALL likewise be covered by a golden fixture file — the trigger for this requirement is "the function is rule-bearing," not "a TypeScript mirror already exists to assert against"; a Go-only rule-bearing package is not exempt from this requirement merely because there is nothing on the other side of the seam to compare it to. Where a change designates one side of a capability authoritative and deliberately builds no mirror of it on the other side, this requirement's cross-language assertion narrows to the side(s) that exist (see `Rule-Bearing Values Are Reproducible Across Build Targets of the Same Language` and `The Golden Fixture Reproduces On Every Build Target` for what a Go-only family is still held to), and the guard against a mirror silently reappearing later is the anti-mirror check named below, not a `pairs` entry in a mirror map — a mirror map `pairs` entry asserts a mirror exists; an anti-mirror check asserts one does not. The system SHALL maintain, for each cross-language golden fixture file under `fixtures/`, a golden contract for every function shared between the corresponding Go implementation and its TypeScript mirror, grouped into named families (one family per shared function). The system SHALL maintain a mirror map naming every function defined in both a Go package and its TypeScript mirror, whether or not exported on either side; each pair in the map SHALL appear in a fixture family or in the coverage inventory. A mirror map for a capability designated Go-sole-authority (no TypeScript mirror) SHALL instead run in anti-mirror mode: it SHALL fail if any function name is declared in both the Go package and the designated non-mirror TypeScript directory, unless that name appears in an explicit, empty-by-default `sharedNames` allowlist recorded in the pair's mirror-map file. That name comparison, and the `sharedNames` allowlist match, SHALL be case-insensitive, because Go exports in TitleCase and TypeScript declares in camelCase, so a case-sensitive comparison never collides on the mirror it exists to catch — `ArcParam` and `arcParam` are the same function under two spellings, and a check that reports "no shared names" for that pair reports a pass for the exact regression it exists to catch; a collision under case-insensitive comparison SHALL be resolved by renaming the TypeScript function to a subject-prefixed, draw-scoped name rather than by widening the allowlist. The anti-mirror check's Go-side name extraction SHALL enumerate every top-level function declared in the authoritative Go package, **whether or not it is exported**, because an unexported Go helper reproduced in TypeScript is the same rule-bearing mirror as an exported one under a different spelling. The anti-mirror check's TypeScript-side name extraction SHALL enumerate every exported declaration in the designated non-mirror TypeScript directory — every line matching an `export` form — **searched recursively through that directory's whole subtree and across both `.ts` and `.tsx` files**, since a scan limited to one directory level or to one file extension reports "no shared names" for a mirror it never looked at, which is a silent pass for the exact regression the check exists to catch — and classify each one into a declaration form the extractor recognizes (`function` declarations, arrow-function and function-expression bindings, class methods, and re-exported aliases); an exported declaration the extractor cannot classify SHALL fail the check, naming the offending file and line, rather than being silently skipped and counted as a pass, because a check whose extractor silently misses a form reports "pass" for the exact regression it exists to catch. `fixtures/board/cases.json` is the board-math instance of this discipline, asserted by `backend/board/fixtures_test.go` and `frontend/lib/board/fixtures.test.ts`; `fixtures/polar/cases.json` is the lattice-core instance, asserted by `backend/polar/fixtures_test.go` and `frontend/lib/polar/fixtures.test.ts`; `fixtures/market/cases.json` is the market-settlement instance, asserted by the corresponding Go and TypeScript settlement suites; `fixtures/space/cases.json` is the first Go-sole-authority instance, asserted only by `backend/space/fixtures_test.go` across the Go build-target matrix, with `frontend/lib/space` (render-only, if it exists at all) governed by the anti-mirror map instead of a `pairs` entry — all follow the rules below identically except where a rule is explicitly scoped to a mirrored pair. The Go and TypeScript test suites for a given mirrored fixture file SHALL assert their implementation reproduces every case in the file byte-for-byte; a Go-only fixture file SHALL be asserted byte-for-byte by its Go suite across the build-target matrix. A change to a shared function's behavior SHALL either reproduce the existing fixture unchanged or re-record it within the same change — a fixture update authored without the corresponding mirror-side change passing is not a valid state to merge (for a Go-only family, "the corresponding mirror-side change" means the change's own Go build-target matrix, not a TypeScript suite that does not exist). Re-recording SHALL be performed as a reviewable diff in the change's own commits; no automated pipeline SHALL regenerate a fixture file. A shared function whose input domain is enumerable within 10^6 inputs SHALL carry an exhaustive-sweep case in its fixture family: a digest recorded over the function's output for every input in that domain, in a canonical serialization both languages reproduce. For a function whose domain is a pair of polar cells, that domain is all ordered pairs of cells with ring indices at or below the sweep case's recorded maximum ring under the schedule the case names, enumerated by `fromRing`, then `fromSlot`, then `toRing`, then `toSlot`, all ascending, and the digest is the SHA-256 hash of the newline-joined decimal `ring:slot` serialization of the function's output for each input, in that fixed enumeration order both languages reproduce; where a function's domain is a cell pair plus additional parameters, the sweep is taken over the cell-pair domain at parameter values recorded in the fixture case, and a list-valued output is serialized as its cells' `ring:slot` forms joined by `,` on that input's line. A rule-bearing function whose input domain is not enumerable within 10^6 inputs — a continuous R³ or R² domain, as in `backend/space` — SHALL instead carry a pinned randomized-sweep case: the fixture record SHALL name the pseudo-random generator and its integer seed, the input box each coordinate is independently drawn from, the case count, and a SHA-256 digest computed over the newline-joined canonical serialization of the function's output for each drawn input, in draw order; the generator SHALL be pure integer arithmetic (for example `splitmix64` on an `int64` state), so the drawn inputs themselves are exactly reproducible on every build target the family is asserted on. The record SHALL additionally pin the mapping from the generator's integer output to a drawn coordinate (a form using only exact operations, for example `float64(u >> 11) * 0x1p-53`, scaled and offset onto the recorded box with an explicit `float64(...)` conversion around the product (`lo + float64(f*(hi-lo))`), so no fused multiply-add can reach a drawn coordinate on a contracting build target), the order in which an input's coordinates consume generator words, and the exact output serialization, which SHALL be a lossless binary-exponent form (`strconv.FormatFloat(v, 'b', -1, 64)` and its equivalent) rather than any decimal form, with a multi-component output serialized as its components joined by `,` on that input's line and an error outcome serialized as a fixed sentinel token — because a decimal serialization cannot express the last-ULP divergence the sweep exists to catch, and an unpinned draw mapping means the same seed selects a different domain in a re-recording. Hand-selected cases document intent; the exhaustive or randomized sweep is what makes the family a contract, because a divergence that occupies a small fraction of the input domain cannot be hand-selected for by someone who does not yet know it exists. A family whose function is under an open cross-target divergence defect SHALL record its sweep case as part of the change resolving that defect, and SHALL be named in the capability's deviation register until then (see `The Capability's Deviation Register Bridges Known Violations Across Its Checks`). Each fixture family SHALL cover exactly one shared function. A shared function with no fixture family SHALL be listed in the coverage inventory with the change expected to cover it; a rule-bearing shared function SHALL NOT remain in the inventory across more than one change that modifies its package.

#### Scenario: Both languages assert the same fixture file
- **WHEN** the Go and TypeScript test suites run against an unmodified `fixtures/board/cases.json`
- **THEN** both suites read every case from that one file
- **AND** both suites pass, having independently reproduced every recorded case

#### Scenario: A one-sided Go change fails the golden fixture
- **WHEN** a change alters a shared function's behavior in `backend/board` without re-recording `fixtures/board/cases.json` or updating `frontend/lib/board` to match
- **THEN** `backend/board/fixtures_test.go` fails on the case(s) whose recorded output no longer matches the new Go behavior

#### Scenario: A re-recorded fixture the mirror doesn't reproduce fails
- **WHEN** `fixtures/board/cases.json` is re-recorded from a new Go implementation but `frontend/lib/board` is not updated to reproduce the new values
- **THEN** `frontend/lib/board/fixtures.test.ts` fails on the case(s) whose recorded output the unmodified TypeScript implementation cannot reproduce

#### Scenario: An exhaustive sweep case pins a function over its whole domain
- **WHEN** the Go and TypeScript suites each recompute a sweep case's digest from their own implementation
- **THEN** both digests equal the recorded digest
- **AND** a divergence on any single input in the swept domain fails the case, even when every hand-selected case in the same family reproduces

#### Scenario: An uncovered mirrored function is caught by the coverage inventory check
- **WHEN** a function is defined in both a Go package and its TypeScript mirror (exported or not)
- **THEN** the capability's mirror map names the pair, and the pair appears either in a fixture family or in the coverage inventory
- **AND** the check fails if a function in either mirror is absent from the map

#### Scenario: A fixture-only change runs both language suites in CI
- **WHEN** a commit or merge request modifies `fixtures/board/cases.json`
- **THEN** the CI stage running `backend/board/fixtures_test.go` and the CI stage running `frontend/lib/board/fixtures.test.ts` both execute for that commit or merge request, regardless of whether `backend/**` or `frontend/**` files are also touched

#### Scenario: A fixture file that differs from its committed content fails CI
- **WHEN** the CI stage running the fixture suites completes
- **THEN** the pipeline fails if any file under `fixtures/` differs from its committed content (`git diff --exit-code -- fixtures/`), because re-recording is only valid as a reviewable diff in a change's own commits, never as an uncommitted or pipeline-generated side effect

#### Scenario: A rule-bearing Go-only package is bound by this requirement despite having no mirror
- **WHEN** a change introduces a rule-bearing Go package that computes persisted values, solve results, or ETAs, and deliberately builds no TypeScript mirror of it
- **THEN** that package's rule-bearing functions are still covered by a golden fixture file, asserted across the Go build-target matrix
- **AND** the absence of a TypeScript mirror does not exempt the package from this requirement

#### Scenario: A randomized sweep pins a function over a non-enumerable domain
- **WHEN** a fixture family's randomized-sweep case is recomputed from its recorded PRNG, seed, input box, and case count
- **THEN** the recomputed digest equals the recorded digest
- **AND** the same PRNG and seed reproduce the identical sequence of drawn inputs on every build target the family is asserted on

#### Scenario: A Go-sole-authority capability's mirror map runs in anti-mirror mode
- **WHEN** `check-mirror-map.sh` evaluates the mirror map for a capability designated Go-sole-authority
- **THEN** it fails if any function name is declared in both the Go package and the designated non-mirror TypeScript directory and that name is absent from the map's `sharedNames` allowlist
- **AND** it does not require — and a normal `pairs` entry SHALL NOT be added to assert — that a TypeScript implementation of any such function exists

#### Scenario: A lower-camel twin of an authoritative Go export fails the check
- **WHEN** the designated non-mirror TypeScript directory declares a function whose name differs from an authoritative Go export's name only by letter case
- **THEN** the check exits non-zero, naming that name as a collision
- **AND** it does not report a pass on the grounds that the two spellings differ

#### Scenario: A declaration form the extractor has no rule for fails the check rather than passing
- **WHEN** the designated non-mirror TypeScript directory declares a function in a form the anti-mirror extractor has no extraction rule for
- **THEN** the check exits non-zero naming that file and line
- **AND** it does not report a pass on the grounds that no name collision was found

#### Scenario: A twin in a subdirectory or a .tsx file fails the check
- **WHEN** the designated non-mirror TypeScript directory declares a case-insensitive twin of an authoritative Go function in a **subdirectory** of that directory, or in a `.tsx` rather than a `.ts` file
- **THEN** the check exits non-zero, naming that name as a collision
- **AND** it does not report a pass on the grounds that the file lay below the directory's top level or carried a different extension

#### Scenario: An unexported Go function counts as an authoritative name
- **WHEN** the designated non-mirror TypeScript directory declares a case-insensitive twin of an **unexported** top-level function in the authoritative Go package
- **THEN** the check exits non-zero, naming that name as a collision
- **AND** it does not report a pass on the grounds that the Go function is unexported
