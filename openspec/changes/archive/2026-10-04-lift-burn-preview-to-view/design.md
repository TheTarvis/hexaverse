## Context

`SpaceCommandPanel` calls `useBurnPreview` itself (`SpaceCommandPanel.tsx:109-115`), the only production call site. A later link (`add-burn-cost-overlay`) needs the same quote in `VitalsStrip`; a second hook instance would double the request rate against an endpoint the live requirement prices at exactly one request per interval. So the quote is lifted to the mounting view first. The lift is HOW and takes no requirement of its own. The behaviour is two request preconditions the code never enforced (a running mine; the selected target being the acting fleet's own host) stated against what the view has last read, and the presentation that follows from not requesting.

Adversary round 1 and the panel's UX review then grew the change into a redesign of when and why the burn command is unavailable (49 tasks). FULL-AUTO RULING 16 of `docs/handoffs/lift-burn-preview-to-view-rulings.md` narrowed it back: that redesign is the follow-up `docs/handoffs/followup-explain-withheld-burn-command.md`, and this change is the lift, the two preconditions, their consequences, and tests that observe every term of the call-site flag. **The burn command's availability is unchanged from today in every state.** Entry mode: specced; the delta targets `openspec/specs/system-space-view/spec.md`.

Facts of the code this design rests on (read at `a1d1c8d`):

- **The selection has one setter.** `SystemSpaceView.tsx:821` - `onSelect={(picked) => setSelection((current) => toggleSelection(current, picked))}`. The selection is not in the URL. `SpaceSelection` has no kind tag: a body, a station and a gate are all `bodyId`; a point is `point` and has no `bodyId`.
- **The acting fleet is derived.** `acting = allFleets.find((f) => f.id === actingFleetId) ?? here[0] ?? null` (`:295-296`), where `here` excludes fleets in transit (`:291-293`). It changes with no handler running whenever the own-fleets read lands differently.
- **A fleet in lane transit can be the acting fleet in exactly one arrangement.** `selectFleet` (`:664-677`), which both the roster row (`:999`) and the strip chevron (`:1014`) call, navigates away for a transit fleet and never sets it acting (`:666-669`). The canvas hands the view a raw `setActingFleetId` (`:827`), but fleet marks are built from `here` (`:462`), so no transit fleet has a mark to activate. An implicit acting fleet (`here[0]`) that departs stops being acting in the same render. What remains: a fleet **explicitly chosen while present** (row, chevron or mark), which the own-fleets read then reports with a served `jump`. `allFleets.find` still returns it, so it is acting and in transit from that read until the departure hand-off's navigation (`:651-660`, `router.push('/')`) unmounts the view. The state exists only in that window.
- **The running mine is one value in the view, already handed to the command panel.** `runningMine = useRunningMine(acting?.id ?? null).data ?? null` (`:422`), and `mineRunning = !!runningMine && runningMine.eta > worldTime` (`:739`) is passed to `SpaceCommandPanel` (`:901`), which uses it for Burn's `disabled` and for Jump's. The preview flag reads that same `mineRunning`. `FleetActionsPanel` calls the same hook for its own gate and also keeps a panel-local `committedEta`; that second derivation and its known defect are not this change's (Non-Goals, Risks).
- **The running-action read's lifecycle.** One inbox query per fleet (`queryKeys.actions.running(fleetId)`), `staleTime` 60 s, `gcTime` 5 min. A fleet never read before has no `data`, so `runningMine` is null (no mine taken to be running); a fleet read within the cache window has its previous answer; a failed refetch keeps the previous `data`. A mine commit and a mine cancel both invalidate this key (`use-actions.ts`), so the view's value follows the refreshed read. The same inbox query is also issued, at mount, for every own fleet present in the system: `ScanSweepWatcher` (`:769-779`) mounts `useRunningScan(fleet.id)` per fleet in `here`, on the same key. Only a fleet in `here` can be made acting (`selectFleet`, the fleet marks), so a fleet that becomes acting has normally been read already, and the "not yet read" window is that mount-time read still pending, not a read first issued at the switch.
- **Attachment is a served id that equals a served body id.** `dockedFeature` is found by `f.id === acting.attachedTo` (`:683`); the live spec states a gate body's served `id` is "the same id that fleet's `attachedTo` reports once it arrives".
- **The hook returns nothing while disabled.** `use-burn-preview.ts:76-77`: `preview = enabled ? data : null`, `failed = enabled && !!query.error`. A suppressed preview is withdrawn at once and is neither `noQuote` nor `stale`. Its `retry` calls `query.refetch()` (`:72-74`), which React Query runs even on a disabled query. A disabled observer stays subscribed and keeps the cache entry's `data`, so `gcTime: 0` does not drop it: when `enabled` flips back to true the observer returns that old `data` at once (with no request at all if it is under `staleTime`, 10 s, old), and `stale` is false, so today the view's `currentQuote` would be the pre-withholding quote (adversary r2 M1; RULING 17).
- **What the panel shows today.** Burn is `disabled={!selection || !canvasAvailable || !fleet || mineRunning}` (`SpaceCommandPanel.tsx:314`); the uncapped label renders whenever there is no current quote (`:302-307`), including with nothing selected and while Burn is disabled by a mine.
- **What the server does with a mid-mine fleet and a zero-length solve.** It refuses the preview for a mid-mine fleet (`backend/fleet/service.go:987`, `ErrPreviewChannelHeld`) and accepts the commit, cancelling the run silently (`docs/handoffs/defect-burn-cancels-running-mine.md`). A zero-length solve is an unmapped 500 (`docs/handoffs/defect-zero-length-burn-returns-500.md`). Today both come back as a failed first preview: a no-quote line, a retry that fails again, and an uncapped label.

## Goals / Non-Goals

Goals: one hook call site; one derivation of "current quote"; the mine and docked-at-target preconditions enforced at that call site, worded against the view's last read with the lag stated; the preview flag and the command panel's mine gate reading one value; the panel's harness migrated to props; a guard that keeps the call site single; every term of the flag observed at the real call site, present and absent; a resumed preview that presents nothing from before the withholding and is requested at the transition.

Non-goals: any change to when the burn command is available, any stated reason for it, any accessible description of it, and any fail-closed handling of a pending or failed running-mine read (`docs/handoffs/followup-explain-withheld-burn-command.md`); the single-reader refactor of `FleetActionsPanel` and its never-cleared `committedEta` (same file); clearing the preview when an order commits (`docs/handoffs/drift-preview-does-not-clear-on-commit.md`, Decision 5); rendering a commit's stranding warning (`docs/handoffs/drift-commit-stranding-warning-not-rendered.md`); the gauge overlay and anything passed to `VitalsStrip`; the fan-in requirement; drawing the preview curve (`docs/handoffs/drift-preview-curve-never-drawn.md`); any backend change, including the zero-length 500 and whether a burn cancels a running mine; any selection-behaviour change; the loading-window uncapped label and the drift notice that outlives its target (`docs/handoffs/defect-command-panel-residual-presentation.md`); reverting, retro-specifying or building on U1-U10 (`docs/handoffs/add-vitals-strip-qa-reverify.md`).

## Decisions

1. **One call site, in `SystemSpaceView`.** The view calls `useBurnPreview` once, after `mineRunning` is derived (`:739`; nothing between `:422` and `:742` returns early), and passes the state to the panel. Alternative rejected: a React context for the quote (RULING 6) - a third consumer surface with no requirement behind it. Alternative rejected: passing the quote to the strip as an unused prop now (RULING 1). Alternative rejected: lifting `useOrder` too, so the view owns the commit - it rewrites the panel's commit tests for a component link 4 retires.

2. **The panel's quote props (flat, all required, testids unchanged).**

   | Prop | Type | Meaning |
   | --- | --- | --- |
   | `preview` | `BurnPreview \| null` | The figures to show; may be stale. Drives the figure list, `preview-affordable`, `preview-stranding` and the unaffordable styling exactly as today. |
   | `currentQuote` | `BurnPreview \| null` | `preview` when it is not stale, else null. The only source of the ceiling, of `maxFuelTons`, and of the previewed half of the commit record. |
   | `previewStale` | `boolean` | Shows `preview-stale` and, with `previewNoQuote`, `preview-retry`. |
   | `previewNoQuote` | `boolean` | Shows `preview-no-quote`. |
   | `onRequote` | `() => void` | The hook's `retry`. Called by `preview-retry` and by a cap rejection. |

   The view derives `currentQuote` in one expression (`preview && !stale ? preview : null`) and the panel does not re-derive it: its line `:119` is deleted, not moved. No effect copies the quote into component state. All five are required so the single production caller cannot omit one silently; the test `panel()` helper supplies defaults. The types come from `@/lib/types/fleet`, so the panel has no import of any kind from `@/hooks/use-burn-preview` (Decision 7 depends on that). Every existing panel testid is kept and none is added; `frontend/e2e/helpers/space-view.ts` reads only `preview-panel` and `burn-button`; the specs also read the four figure ids (`e2e/tests/space-journey.spec.ts:160-170`: `preview-arrival`, `preview-deltav`, `preview-fuel`, `preview-fuel-ceiling`), for a freshly spawned, unattached fleet with no mine, where the preview is still requested. `preview-panel` is the panel's always-mounted root, so no existing wait on it depends on when a quote lands. The `mineRunning` prop stays, for Burn's and Jump's `disabled`, unchanged. Alternative rejected: one `quote` object prop - a new exported type and constructor in a shared module for one consumer. Alternative rejected: the panel keeps deriving currency, leaving two derivations for the overlay to disagree with.

3. **Call-site flag, one expression, one value per term.**

   ```ts
   const dockedAtTarget =
     !!acting?.attachedTo && selection?.bodyId !== undefined && selection.bodyId === acting.attachedTo
   const previewWanted = !!acting && !acting.jump && !mineRunning && !dockedAtTarget
   ```

   `previewWanted` is the hook's `commitWouldBeAccepted`. Its argument name is kept (the hook's signature is fenced) although two of the terms are not about acceptance. The transit term is today's `!fleet.jump`, carried unchanged out of the panel. The mine term is the `mineRunning` the view already derives and already hands the panel for Burn, so the preview request and Burn's mine gate read one value and change in the same render (the spec's "change together" scenario). The flag has no canvas term and no commit-in-flight term (the preview keeps being requested for a held selection through a context loss, as today) and no burning term: a fleet with a running burn is previewed (Decision 8's table). Because the hook returns no quote while disabled, a term that becomes true while a preview is shown withdraws it at once. The selection is never touched.

4. **Docked-at-target guard: id equality on two served fields, no kinds, no geometry.** `attachedTo` and the selected `bodyId` are both ids the server served; the guard is their equality and nothing else. No client rule mirrors Go. Both operands must be present - the naive `selection?.bodyId === acting.attachedTo` is true for a free-flying fleet (`attachedTo` absent) with a point selected (`bodyId` undefined) and would suppress the commonest point preview in the game. A point selection therefore never matches, including a point that coincides with the host: detecting that would need a client distance rule, so that request is still sent and the server still answers for it. The guard is a precondition on the preview request only; the burn command path stays the one uniform path, its availability unchanged, and the selection untouched. Alternative rejected: clear the selection on dock - rewrites *Toggle-to-Deselect*. Alternative rejected (RULING 8, deferred by RULING 16): make Burn unavailable there with a stated reason - the follow-up's.

5. **The commit clause is deferred (RULING 13).** This change does nothing when an order commits. After a successful commit the selection is kept and the preview keeps refreshing exactly as it does today, as a re-target quote; a second Burn stays capped by that quote and `preview-stranding` stays on screen. The live sentence "SHALL clear ... when an order commits" is carried in the MODIFIED block as live text and remains unimplemented: that is recorded drift (`docs/handoffs/drift-preview-does-not-clear-on-commit.md`), owned by link 2a-iii `clear-burn-preview-on-commit`. There is no stored commit record in the view and no commit callback from the panel.

6. **A suppressed retry sends nothing.** The hook's `retry` becomes a no-op while the query is disabled. Without it the lifted `onRequote` can issue a request the requirement forbids: a cap rejection that lands after the selection moved to the fleet's own host calls `retry()` on a disabled query and sends the zero-length preview. The no-op reads the live enabled state (a ref or the observer's current options), not a value captured at click time: the panel's mutate-level `onError` is captured when Burn is clicked, when the preview was still enabled, so a check on a captured `enabled` would still call `refetch()`. Signature unchanged. The same no-op is what makes the spec's precedence over *A Burn Commit Is Quote-Locked*'s re-quote true (RULING 17, M2): the rejection calls `onRequote`, which sends nothing, and with no preview there are no figures to re-confirm. The re-quote obligation resumes with the preview, because `retry` is live again whenever the query is enabled.

7. **Static guard.** A test in the idiom of `lib/realtime.test.ts` (walk `app`, `components`, `hooks`, `lib`; skip test files) asserts: exactly one module imports `use-burn-preview` by any path, it is `components/space/SystemSpaceView.tsx`, and that source contains exactly one `useBurnPreview(`. Two calls in one module double the request rate as surely as two modules do.

8. **Every term of the flag is observed at the real call site.** `drift-running-mine-preview-unsuppressed.md` happened because the flag's only tests passed it into the hook by hand. After the lift the flag is a new expression in the view, so each term, including the one that must be absent, is observed in `SystemSpaceView.burn-preview.test.tsx`, which renders the real view and command panel with `useBurnPreview`, `useRunningMine` and the mine and cancel mutations real, mocks the reads the existing family already mocks, and mocks the services (`fleetService.preview`, `actionService.listRunning`, the mine commit and cancel services), the own-fleets read, the stage (exposing body, gate-body, point and fleet-mark triggers) and the router. Every test makes a selection, and each term has an arrangement where it withholds and one where it must not:

   | Term | Withholds | Must not withhold |
   | --- | --- | --- |
   | Running mine (`mineRunning`) | Mine known to the running-action read, then a non-host body selected: no call. A preview shown, then a mine committed through the real fleet panel and reported by the refreshed read: figures go, no further call. Selection held, acting fleet switched by the roster row to a mining fleet whose read is deferred: at most the starting call and one per elapsed interval until the answer, then none | The mine ends by ETA passing: a call for the held selection. The mine ends by cancel through the real cancel control and the read answers no mine: a call. The switch's read answers no mine: calls continue |
   | Lane transit (`acting.jump`) | The only reachable arrangement: fleet chosen through the roster row while present, a body selected and previewed, then the own-fleets read reports it with a served `jump`, router mocked so the view stays mounted: figures go, no further call, one hand-off navigation. A test that puts a transit fleet in the read and then "chooses" it cannot be written against the unmocked view | Every other test: a present fleet is previewed |
   | Docked at target (`dockedAtTarget`) | Acting fleet attached to a selected station, and to a selected lane-gate body: no call across several intervals, selection unchanged. A previewed body the own-fleets read then reports the fleet attached to: figures go | Left host (the read reports no attachment): a call for the station's body. Docked with a different body or a point selected: a call. A free-flying fleet (no `attachedTo`) with a body and then a point selected: a call for each (the absent-equals-absent guard) |
   | Burning (no term) | none | Acting fleet serving a running burn toward body A (`state.Mode === 0`, a served `Burn`), unattached, not in transit, no mine; body B selected: `fleetService.preview` called once with that fleet's id and the request naming B, figures render, `burn-button` enabled, one further call per interval. An implementer who adds a not-burning term fails it |

   Each reachable withheld-to-requested transition also has a shown, withheld, restored arrangement with the restoring request held pending (Decision 13): the mine ending by ETA, the mine ending by cancel, and the fleet leaving its host (a body previewed, the own-fleets read reporting the fleet attached to it, then reporting it detached). Lane transit never returns while the view is mounted, so that term's resume is observed at the hook, where the flag is the only input.

   The burning row's "alongside the running burn's own curve" clause is the stage's and is not asserted (the preview curve is undrawn; `drift-preview-curve-never-drawn.md`). In the cancel arrangement the mine is one the running-action read reports, not one committed in this mount, so the view-level observation does not depend on `FleetActionsPanel`'s never-cleared `committedEta`, which gates only that panel.

9. **The withheld state is withheld, not failed.** A request that is never sent is not a failed one: `noQuote`/`stale` are false, so the panel shows no figure, no no-quote line, no stale line and no retry. This is what the hook already returns; the spec states it.

10. **The uncapped label follows Burn's own availability.** The panel computes `burnAvailable = !!selection && canvasAvailable && !!fleet && !mineRunning` - the negation of Burn's existing `disabled` expression, which is not edited - and renders `burn-uncapped-label` only when `burnAvailable && !currentQuote`. Today it renders whenever there is no current quote. The spec enumerates the four unavailable states (no selection, no acting fleet, canvas unavailable, a running mine) rather than saying "unavailable for any reason", so the double-submit window, which the live *Burn and Jump Commit Controls Guard Against Double-Submit* governs and whose rendered `disabled` has no in-flight term (`SpaceCommandPanel.tsx:314`; unverified whether that is drift), is not pulled in. Where Burn is available and no preview is requested (docked at the target, lane transit) the label still renders, as today; it is a true statement there (the burn is submitted with no ceiling). Alternative rejected: also state a reason line beside the unavailable Burn (RULING 8, deferred).

11. **A jump needs nothing of its own.** A committed jump puts the fleet in transit, which the flag already reads, and the acting fleet's departure navigates away.

12. **The running mine is not refactored.** The preview flag and Burn's mine gate read the view's one `mineRunning`. `FleetActionsPanel` keeps its own read and `committedEta`; the cut-drive, stop and mine gating there are as today. That the two panels can disagree in two windows (after a mine commit until the invalidated read lands; after cancelling a run committed in this mount) is pre-existing and is the follow-up's (Risks).

13. **The hook holds no earlier answer across a withheld period (RULING 17; adversary r2 M1).** Mechanism, at the hook and inside its fenced signature: when `enabled` goes false the hook cancels any request in flight for its key and discards the cached answer for that key (an effect keyed on `enabled`, calling the query client's cancel and remove for `queryKeys.fleets.burnPreview(fleetId, selectionKey)`), so that when `enabled` goes true again the observer has no `data`, is enabled with no data, and therefore fetches at once - at the transition, not at the next interval. Until that response lands `preview` is null and `stale`/`noQuote` are false, so the panel shows no figure and `currentQuote` is null, and a click carries no `maxFuelTons`; if the request fails the state is `noQuote` (no data, an error), never `stale`. The rule is the hook's, so, for the same acting fleet and selection, it holds for every term of the flag at once (a changed fleet or selection is already governed by the replace rule), including those not reachable back at the view (lane transit never returns while the view is mounted) and those that are (mine end by ETA or cancel; the fleet leaving its host). The effect writes no component state, so *Animation Never Re-Renders the View* is untouched. The in-flight request is cancelled so that a response landing during the withholding cannot be what the resumed preview shows. The cancellation is at the query layer: removing the cache entry destroys the query, which cancels its fetch silently, and the still-mounted observer is re-pointed at a fresh, empty query by the cache's build on the render where `enabled` returns to true (read against the installed query-core 5.90.11). The HTTP request itself is not aborted, because `fleetService.preview` takes no abort signal and its signature is not changed here; its response is discarded. The effect depends on `enabled` and on the two parts of the key (fleet id, selection key), and does nothing while enabled. The pending window shows the loading-window presentation already filed (`defect-command-panel-residual-presentation.md` item 1): no figure, uncapped label beside an enabled Burn. Alternative rejected: let the earlier figures reappear with a stated age bound - it keeps a cap derived from a pre-mine quote, which link 2a-iv would draw on the fuel gauge. Alternative rejected: a client-side age check in the view over `dataUpdatedAt` - a second derivation of currency beside Decision 2's one, and it cannot make the request go out at the transition. Alternative rejected: a counter in the query key bumped on each resume - it needs a ref or state written during render to detect the transition.

## Risks / Trade-offs

- A quote refresh now re-renders the view, not the panel. It is a 10 s cadence beside an existing 1 Hz tick; `SystemSpaceView.render-loop.test.tsx` is the guard and must stay green.
- **Lag, stated rather than denied.** The mine and attachment states are what the view last read. (a) A newly acting fleet's running-mine read has not answered: `data` is undefined, no mine is taken to be running, and a preview request goes out (one at the switch, then one per interval) until the read answers; if the fleet is mining the server refuses it and the player sees a failed first preview with an uncapped label beside Burn, which is today's presentation, for at most that window. (b) A mine committed from this view is reported by the refreshed read one round trip later; until then the preview stays shown and Burn stays enabled, as today. (c) A failed running-mine read with no earlier answer keeps the same "no mine" reading indefinitely, so a mining fleet's preview is requested and refused every interval and Burn is offered over a mine the server will cancel silently; that exposure predates this change, belongs to `defect-burn-cancels-running-mine.md` on the server side and to the follow-up's fail-closed handling on the client side. (d) A cached "no mine" less than a minute old, or a mine begun from another tab or the agent, is used. (e) Attachment: between a fleet's arrival at its still-selected target and the own-fleets read reporting it, one request per interval may go out and the server answers the zero-length solve with a 500 (filed); the ETA-scheduled refetch normally lands just after a served arrival. When a read reports the change the term applies in that render with no handler involved. Nothing is withheld on `isFetching`, which would withdraw the quote on every poll.
- Docked at the selected target, Burn stays enabled and a click ends in the server's 500 and the generic error copy, as today. The change removes the 500 polling and the unsatisfiable Retry; it does not remove the dead end (UX F1; the follow-up). It also loses the one line that hinted the burn cannot be solved there: today the panel shows "No quote - the preview could not be solved", Retry, the uncapped label and an enabled Burn; afterwards it shows only the uncapped label and an enabled Burn, which looks like the loading window (`defect-command-panel-residual-presentation.md` item 1), permanently, for the ordinary state after every arrival. That residue is accepted under RULING 16 and recorded in `docs/handoffs/followup-explain-withheld-burn-command.md`.
- A resumed preview has an empty pending window (Decision 13): from the transition until the restoring response there is no figure and the uncapped label is shown, as in the loading window. That is accepted over showing a pre-withholding quote as current.
- The restoring request at a mine's ETA can be refused once. The flag flips at the first coarse tick after the ETA, while the server's preview path settles a due burn but not a due mine (`backend/fleet/service.go:526`, `:987`): until some other read settles the run (the view's own ETA-scheduled refetch, at the ETA plus `ETA_CUSHION_MS` and a round trip) the server still answers `ErrPreviewChannelHeld`. If the restoring request wins that race the panel shows the no-quote state and Retry, which is what the spec's "failed restoring request" rule prescribes, and the next interval heals it. Not a regression: today every preview request during and just after the mine is refused the same way. The tier-4 journey must not assert that the quote returns without that state.
- During a mine, the command panel's disabled Burn still carries no reason (UX F3, reason half; the follow-up).
- The preview still does not clear on commit (Decision 5). `add-burn-cost-overlay` must not be authored against a quote lifetime that assumes it does until 2a-iii lands.
- The seven view test files mock `useRunningMine` as `{ data: null }` and the preview hook in the wrong shape; `{ data: null }` reads as answered, so they pass before and after, and correcting the preview mock is hygiene, not a red step.
- `FleetActionsPanel` is not edited, so no behaviour the live `docked-fleet-actions` text states changes.

### Carried scenario bodies edited

No carried scenario is dropped and no carried heading is changed.
